### OPEN — the question the user asked last, answered but not resolved
"Is the database approach okay?"

**Critical finding: the 1,717-line functions codebase touches Firestore in exactly ONE place**
(`firebase-functions/src/index.ts:185`, reading a user doc for the usage check). Everything else is
an OpenRouter proxy + Firebase Auth token verification. **So "reuse the backend" is NOT an argument
for keeping Firestore as the ledger** — the proxy works over any database.

Argument made against Firestore-as-ledger:
- Every new business tool (`get_profit_loss` etc.) is a GROUP BY. Firestore has no GROUP BY.
  `sum()`/`avg()` exist but without grouping → one query per category per period
  (12 months × 20 categories = 240 queries). **Flagged to user as worth verifying against current
  Firestore docs — aggregation support has moved and knowledge may be stale.**
- Per-document-read billing + reports that scan the ledger = most common action is most expensive.
- Volume: personal ~30 tx/month vs business ~200+; 12,000 docs touched by a 5-year P&L.
- Each Ask turn fires 2-4 tool calls, each its own scan.
- CashMonki's existing `spendingByCategoryRows` / `comparisonRows` read-all-and-reduce-in-Swift.
  Fine at 333 transactions, degrades at business scale.
- Rollup-doc mitigation works but drifts under edits/backfills/CSV imports — all constant in a
  business app.

**Recommended: Firebase Auth + Cloud Functions + Postgres (Supabase) for the ledger.** ~1 day to
wire Firebase JWTs into Supabase RLS. User already knows Supabase (Supabooks, Bambooks,
Outreach Captain). Alternative offered: all-Supabase, giving up ~1,700 lines of reusable proxy.

**Awaiting user's call: hybrid vs all-Supabase.** Then deliver the full build plan —
schema, 11 Ask tools, Compose module structure.
